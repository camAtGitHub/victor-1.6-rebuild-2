Build a Vector Light Cube

A start-to-finish guide for rebuilding or cloning Anki Vector’s interactive cube — from Dialog DA14580 hardware through BLE protocol, vision markers, shell, and robot verification. Reverse-engineered from robot/cube_firmware/ in this tree (Vector 1.6 rebuild).

MCU: Dialog DA14580 Accel: Bosch BMA253 44×44×44 mm BLE 4.x peripheral 1.5 V N / E90 / LR1 only Not A23 · not Li-ion stock

1. Overview

Official Vector ships with one light cube (Cozmo shipped three). The cube is:

  • Visual: six unique face markers (~23 mm) on a 44 mm cube so the camera can localize and dock.
  • Wireless: BLE peripheral advertising as Vector Cube, streaming accelerometer and battery, receiving light keyframes.
  • Battery powered: single alkaline N-cell (E90 / LR1), ~20–40 hours of active use.
Where the “firmware file” lives resources/assets/cubeFirmware/cube.dfu is only the signed application blob (~3.2 KB). Real source, board pinout, Dialog SDK, and tools are under robot/cube_firmware/. Engine loads the DFU path via CubeCommsComponent and flashes when versions mismatch.

2. Two realistic build paths

Path A — Hardware-compatible

Run stock (or rebuilt) Anki images

  • DA14580 (or carefully qualified 58x) + same pinout
  • BMA253 3-wire SPI
  • 12 LED channels + boost enable
  • 1.5 V cell + Dialog power topology
  • Anki loader + XXTEA DFU + cube.dfu

Best fidelity Hardest PCB / sourcing.

Path B — Protocol clone

Any modern BLE MCU

  • nRF52 / DA14531 / ESP32-C3 / …
  • Implement GATT UUIDs + protocol.h
  • Optional: skip stock DFU; ship your app only
  • Still need 4 RGB corners + accel stream
  • Still need correct vision markers + size

Most practical DIY Engine may still try OTA — handle or ignore.

6. Sensors

Bosch BMA253

  • Chip ID register 0x00 must read 0xFA or cube emits COMMAND_ACCEL_FAILURE.
  • 3-wire SPI bit-banged on Port 0 (ACC_nCS, ACC_SCK, ACC_SDA).
  • ACC_PWR (P0.2) power-gates the sensor.
  • Configured: ±4 g, ~250 Hz BW, FIFO XYZ; streams 3 frames/message.
// robot/cube_firmware/app/accel.c (excerpt)
spi_write8(BGW_SPI3_WDT, 0x01);   // three-wire SPI
spi_write8(PMU_RANGE, 0x05);      // +4g
spi_write8(PMU_BW, 0x0D);         // 250Hz BW
spi_write8(FIFO_CONFIG_1, 0x40);  // FIFO XYZ
// chip_id must be 0xFA

bletool treats 0x2000 raw counts ≈ 1 g when interpreting upright tests.

Battery ADC

On-chip GP-ADC samples VBAT1V about once per second and notifies COMMAND_VOLTAGE_DATA. Host scale used in bletool: adc * 3.6 / 1024 volts (empirical for that tool).

7. Lights & boost

  • 4 corners × RGB = 12 GPIOs (D0…D11).
  • Software PWM via Timer0 at 200 Hz (lights.c).
  • BOOST_EN (P2.0) enables boost for LED power; driven as 1V-BAT domain GPIO.
  • Engine maps NUM_CUBE_LEDS = 4 logical lights.
// LED enum — corner order (lights.h)
HAL_LED_D1_RED/GRN/BLU  // channel 0
HAL_LED_D2_RED/GRN/BLU  // channel 1
HAL_LED_D3_RED/GRN/BLU  // channel 2
HAL_LED_D4_RED/GRN/BLU  // channel 3

Do not put 12 V (A23) or raw Li-ion into a stock-topology board. The DA14580 and boost design assume ~1.5 V primary cell behavior. Redesign UVLO/boost if you change chemistry.

11. Mechanical shell & vision markers

Engine defines light cubes as 44×44×44 mm with 23 mm markers (engine/BlockDefinitions.h). Vector recognizes families LIGHTCUBE1–4 (I/J/K/circle marker sets). Marker textures for simulation (print templates) live in this repo: 

simulator/protos/textures/lightCubes/
Printing markers Print high-contrast, matte, non-glossy. Keep ~23 mm mark size centered on each face. Battery door usually occupies one face — align bottom/top markers with door orientation used by stock cubes. A cube with correct markers and dead battery is still a visual landmark; lights/games need BLE+power.
  • Four vertical edges: translucent windows over RGB LEDs (diffusers).
  • Rubberized corners improve grip / drop survival (stock manufacturing detail).
  • Center mass PCB with battery along one axis; antenna often opposite or beside spring (teardown).

12. Firmware architecture

Two layers share one DA14580:

  1. Resident host / loader (src/user_app/ + Dialog SDK) — BLE stack, custom GATT, XXTEA DFU into SysRAM, tick scheduler.
  2. Application image (app/ → cube.dfu) — lights, accel, animation, voltage, protocol handlers.

15. DFU / OTA flow

  1. Central connects; reads/notifies Loaded Program Version (16-byte ASCII timestamp string).
  2. If version ≠ on-disk cube.dfu header, engine / bletool streams DFU body (skip first 0x10) in 20-byte writes to OTA Write Point.
  3. Loader copies into SysRAM; final short packet triggers XXTEA decrypt + nonce check.
  4. On success: version notify updates; AppInit runs; tick every ~10 ms timer unit.
  5. Runtime commands use Application Write; telemetry via Application Read notify.
Path B note If you implement a clone on non-DA14580 silicon, either (1) always report a version matching the robot’s on-disk DFU so it never flashes, or (2) accept OTA writes and ignore/no-op them, or (3) change robot resources (advanced). Stock robots will attempt OTA when versions differ.

17. Flashing nearby cubes (bletool)

WARNING (from upstream README): bletool flashes all nearby advertising cubes. Don’t run this in a room full of other people’s Vectors. 
cd robot/cube_firmware/bletool
npm install
cd ..
node bletool ../../resources/assets/cubeFirmware/cube.dfu
# or: node bletool ./build/cube.dfu

On match, bletool runs a RGB keyframe test and upright-accel pass/fail lighting.

Robot auto-flash: engine/components/cubes/cubeCommsComponent.cpp sets path assets/cubeFirmware/cube.dfu on the CubeBleClient.

18. Path A — Build order (stock silicon)

  1. Prototype on DA14580 dev kit — bring up BLE advertise as Vector Cube, UART log, current draw in extended sleep.
  2. Port Anki pin map — match board.h; keep P1.2/P1.3 free; wire BMA253 3-wire + power gate.
  3. LED + boost — 12 channels, soft-PWM friendly (no heavy capacitive loading that breaks timing).
  4. Power tree — 1.5 V cell → Dialog DCDC; boost for LEDs; verify VBAT ADC range.
  5. Program loader — burn OTP header / boot path per Dialog; public BD_ADDR unique per cube.
  6. OTA app — flash cube.dfu via bletool; confirm version string and RGB self-test.
  7. RF validation — range with robot (~few meters), concurrent with Wi-Fi environment.
  8. Mechanical fit — 44 mm shell, markers, door, springs, antenna keep-out.
  9. On-robot — freeplay connect, set lights, roll/pop-a-wheelie, WebViz Cubes tab.

19. Path B — Protocol clone (practical DIY)

  1. Pick BLE SoC with good peripheral examples (nRF52 SoftDevice / Zephyr / ArduinoBLE, etc.).
  2. Implement GATT service + 4 characteristics (UUIDs above). Advertise name Vector Cube.
  3. On connect: notify a 16-byte version string equal to the first 16 bytes of the robot’s cube.dfu (currently starts 2018-08-14T17:40…).
  4. Parse Application Write packets per protocol.h; drive 4 RGB LEDs with hold/decay (can simplify).
  5. Notify accel frames (cmd 2) and voltage (cmd 4) at similar rates to stock.
  6. Print / apply vision markers; rigid 44 mm body; corner light pipes.
  7. Validate with phone nRF Connect first, then Vector connection coordinator / WebViz.
Minimum viable clone If you only care about “Vector finds cube and docks,” prioritize markers + size. If you care about light games and tap detection, prioritize BLE protocol + accel + LEDs.

20. Suggested assembly order

  1. PCB SMT: SoC, crystal, RF, accel, boost, passives.
  2. Hand-solder springs / battery contacts; verify polarity silk.
  3. Mount LEDs toward corner light pipes; black out internal light leaks.
  4. Program loader (Path A) or firmware (Path B); functional test on bench with N-cell.
  5. Install PCB in mid-frame; route antenna away from battery metal.
  6. Apply face markers (correct rotation — top vs bottom docking conventions).
  7. Install diffusers / outer shell; torque battery screw gently.
  8. Pull-tab simulation: insert battery last before packing.
